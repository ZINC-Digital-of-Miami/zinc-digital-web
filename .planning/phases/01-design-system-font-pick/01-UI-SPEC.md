## Spacing Scale

Declared values (multiples of 4, per GSD default — spec does not override this):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon/glyph gaps, inline padding |
| sm | 8px | Compact element spacing (label-to-value gap on the spec sheet) |
| md | 16px | Default element spacing |
| lg | 24px | Card/row padding on the spec sheet |
| xl | 32px | Layout gaps between spec-sheet fields |
| 2xl | 48px | Major section breaks within a band |
| 3xl | 64px | Page-level spacing |
| 4xl | 96px | Band vertical padding, mobile |
| 5xl | 128px | Band vertical padding, desktop |

Exceptions:
- `4xl`/`5xl` extend the base 8-point scale (still 4px-multiples) to give the editorial "annual
  report" direction (§8) the large breathing room huge display type needs around it — every full
  band (hero included) uses `4xl` top/bottom padding on mobile and `5xl` on desktop (`≥1024px`).
- Minimum interactive touch target is 44×44px (the "Start an Inquiry" button and the `tel:` link),
  independent of the 4px scale, per standard accessibility practice — not spec-mandated but not
  contradicted by it either.

Shared across all three font pairings (only the `font-family` swaps — see **Font Pairings** for
which family and numeric weight fills each role per pairing). Sizes are mobile → desktop via
`clamp()`, stated as an exact formula so there is nothing to interpret at execution time.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Display (hero core line; only usage in Phase 1) | `clamp(3.5rem, 10vw + 1rem, 12.5rem)` → 56px at 375px / 160px at 1440px / 200px cap at ≥1840px (owner: "big headers"; 96px was too timid for the brief) | Heavy — pairing-specific numeric value (800 Big Shoulders Display / 900 Barlow Condensed / 700 Oswald — see Font Pairings) | 1.05, `letter-spacing: -0.01em` |
| Heading (spec-sheet service name, e.g. "Shopify Ecommerce") | `clamp(1.75rem, 2vw + 1.25rem, 2.75rem)` → 28px mobile / 44px desktop | Same Heavy weight as Display | 1.15 |
| Body (hero supporting line; spec-sheet plain-language line and field values) | 16px mobile / 18px desktop (`clamp(1rem, 0.3vw + 0.94rem, 1.125rem)`) | Regular 400 | 1.5 |
| Label/Mono (spec-sheet field labels — "Deliverables", "Cadence", "Client Owns", "Reported"; the `Text (786) 575-4837` line) | 14px, fixed (no fluid scaling — data/label text stays legible-dense at any viewport) | Regular 400 | 1.4, `letter-spacing: 0.04em`, all-caps for field labels only (not for the phone number) |

## Color

Every figure below is a computed WCAG 2.2 relative-luminance contrast ratio (sRGB → linearized →
`L = 0.2126R + 0.7152G + 0.0722B` → `(L1+0.05)/(L2+0.05)`), not a recalled or spec-copied number —
recomputed independently against the spec's own claims, and all five matched the spec's stated
ratios exactly (§8/§18), so the locked palette is verified correct, not just assumed correct.

| Role | Value | Usage |
|------|-------|-------|
| Ground (alternates by band) | `#0A0A0B` near-black / `#F5F6F7` cool snow white — computed contrast between the two: 18.29:1 | Full-bleed band background. Each band sets exactly one via `data-theme="dark"` / `data-theme="light"` (DSGN-03). Never both, never blended, never gated by `prefers-color-scheme` (see UI Considerations). |
| Body gray — dark ground | `#A6A7AB` — computed 8.24:1 on `#0A0A0B` | Body copy and supporting lines on `data-theme="dark"`. Spec locks "one mid-gray per ground" without a hex; this value is Claude's discretion, chosen to comfortably clear AA (4.5:1) with margin and to share the same cool (B>R) neutral cast as the ground colors themselves. |
| Body gray — light ground | `#5C5D61` — computed 6.08:1 on `#F5F6F7` | Body copy and supporting lines on `data-theme="light"`, same discretion basis as above. |
| Accent — dark bands | `#FC0781` magenta — computed 5.17:1 on `#0A0A0B` | Pulse, strike, highlight, active state on dark bands only. Never a fill/background. Not used anywhere in Phase 1's two surfaces (hero is a light band; spec sheet is light) — declared here because it is part of the one token set every later phase inherits. |
| Accent — light bands, display/graphics | `#07B2B2` teal — computed 2.42:1 on `#F5F6F7` (below the 3:1 AA large-text/graphics floor — must stay strictly decorative, see Research Corrections) | Hero core-line strike-through mark and highlighter-hit mark (decorative layer only, never the headline text's own color) |
| Accent — light bands, small text/links | `#057E7E` teal — computed 4.52:1 on `#F5F6F7`, 4.89:1 on pure white | Any actual teal-colored small text or link on a light band. Not used in Phase 1's two surfaces. |
| Destructive | not applicable | No destructive action exists in Phase 1's scope (static hero + one fixed spec sheet, no form, no delete). |

**Secondary (30%) — not applicable.** The locked palette (§8) is exactly: one ground color per
band, one body gray per ground, one accent per ground. There is no authorized third surface tone
(no card background, no nav strip) — inventing one would exceed the locked token set. Bands are
flat single-ground surfaces.

Accent reserved for — explicit list, nothing else:
- Hero core-line strike-through mark on "the scope" and highlighter-hit mark on "the business"
  (light band → `#07B2B2`, decorative layer, per the resolved conflict below)
- The Loop's line-draw and pulse (Phase 2, `#FC0781` on the Loop's dark band — not built in Phase 1)
- Logo-wall hover/tap flip to accent (Phase 2, dark band)
- Spec-sheet field labels ("Deliverables", "Cadence", etc.) are **never** accent-colored — they
  stay Label/Mono gray. Accent marks kinetic/emphasis moments only, never static data labels.

Enumerated by direct file inspection (`file`, `md5`, and visual read) of the two source
directories named in the phase brief, 2026-09-25. Four unique raster files exist; two filename
pairs are byte-identical duplicates (confirmed by MD5) and are noted, not double-counted.

| Asset | File | Dimensions | Ground it's for |
|-------|------|------------|------------------|
| Circuit-brain mark + arced "ZINC DIGITAL" lockup, black ink | `/Volumes/Satechi Hub/ZINC Digital Agency/Graphics/ZINC Fusion Icons .png` | 2000×2000 | Light bands |
| Circuit-brain mark + arced "ZINC DIGITAL" lockup, white ink | `/Volumes/Satechi Hub/ZINC Digital Agency/Graphics/zinc white fusion icon.png` | 2000×2000 | Dark bands |
| Standalone "ZINC" wordmark (no "Digital", thin geometric sans, no dot on the "i" — per the 2026-05-15 checkpoint doc), black | `/Volumes/Satechi Hub/ZINC Digital Agency/docs/context/brand-assets/zinc-logo-primary-black-transparent.png` (identical MD5 to the `-wordmark-` filename variant — same file, ignore the duplicate name) | 892×221 | Light bands |
| Standalone "ZINC" wordmark, white | `/Volumes/Satechi Hub/ZINC Digital Agency/docs/context/brand-assets/zinc-logo-primary-white-transparent.png` (identical MD5 to its `-wordmark-` duplicate) | 892×222 | Dark bands |

**Not a brand asset for this phase:** `Graphics/ZINC Fusion Icons  (1).png` is a magenta-filled
variant of the same circular mark (confirmed by visual read, MD5 `60443ee4...` distinct from the
black version). DSGN-05 and §8 require the mark to render black-and-white on both grounds — do
not use the magenta file as the default mark. It exists only as raw material if a later phase
wants one deliberate magenta mark-moment (e.g. the footer's "one restrained magenta moment," §6.1
band 9) — not Phase 1's job, and CSS `filter`/masking on the black or white file is the lighter-
weight way to achieve a one-off tint later rather than shipping a third raster variant.

**Usage split:** the circular mark carries its own baked-in "ZINC DIGITAL" text and reads as a
badge/seal — use it where a self-contained mark is appropriate (nowhere in Phase 1's two surfaces
specifically, but available for the hero band's header if the plan calls for one). The standalone
"ZINC" wordmark is the short-form lockup — matches the brand voice's own convention of writing
"ZINC," never "ZINC Digital," in running copy (§7) — use it for compact placements (nav, footer).

**Known constraint — raster only, no SVG source exists** (searched the full `ZINC Digital Agency`
repo tree for `*.svg`; none found). DSGN-05 requires the mark to render "crisply... at mobile and
desktop widths." Mitigation, since re-vectorizing is out of scope for Phase 1:
- Circular mark: safe up to ~1000px on-screen width (half its 2000px source — a retina-safe 2×
  ceiling). Comfortably covers any placement in Phase 1's two surfaces.
- Wordmark: safe up to ~446px on-screen width (half its 892px source, same 2× rule). If a later
  phase needs it larger than that, request a vector re-export before shipping — do not upscale
  past this ceiling (see UI Considerations, flagged unresolved).
- Both: size via CSS `aspect-ratio` from the source's native ratio (mark 1:1; wordmark ≈4.04:1),
  never independent `width`+`height`, so the mark can never be stretched non-uniformly.

## Font Pairings (DSGN-01)

All three self-host, subset to Latin + Latin-1 Supplement via `pyftsubset`, output WOFF2 only, per
`.planning/research/STACK.md`'s subsetting method — that method is unchanged and still correct.
What changed below (flagged in **Research Corrections**) is which of the three families are
actually distributed as variable fonts by Google Fonts; verified live against `google/fonts`
METADATA.pb and the `fonts.googleapis.com/css2` ranged-request API, 2026-09-25.

| Pairing | Display (Heavy role) | Body (Regular role) | Mono (Label role) | Self-hosted files |
|---------|----------------------|----------------------|---------------------|--------------------|
| **A — industrial/editorial** | Big Shoulders Display, variable `wght` 100–900, instance **800** | Inter, variable `wght` 100–900 (+`opsz` 14–32), instance 400 | JetBrains Mono, variable `wght` 100–800, instance 400 | 3, all single-file variable |
| **B — Swiss/grotesk-classic** | Barlow Condensed, **static-only** (no variable axis shipped by Google Fonts — corrected below), instance **Black 900** | Public Sans, variable `wght` 100–900, instance 400 | IBM Plex Mono, **static-only** (corrected below), instance Regular 400 | 3 (1 variable, 2 static single-weight) |
| **C — contemporary/warmer grotesk** | Oswald, variable `wght` **200–700 only** (corrected below), instance **700** (its ceiling, not 900) | IBM Plex Sans, variable `wght` 100–700 (+`wdth` 75–100), instance 400 | Space Mono, static Regular/Bold only (already flagged by STACK.md), instance Regular 400 | 3 (2 variable, 1 static single-weight) |

All three licenses are SIL OFL except JetBrains Mono (Apache 2.0) — all open-license,
self-hostable, none is Archivo (excluded per §8/STACK.md).

**Owner-visible consequence of the correction:** Pairing C's display face cannot reach the same
"black/heavy" weight A (800) and B (900) can — its heaviest instance is 700. This is a real,
visible difference in how loud the hero reads at huge display size, worth the owner seeing named
this way rather than discovering it only by eye.

Metric-matched fallback (DSGN-04, CLS 0, Pitfall 6): for each of the nine files above, compute
`ascent-override` / `descent-override` / `line-gap-override` / `size-adjust` at build time from
the actual font's own metrics — using a tool (Fontaine or capsize), not hand-typed numbers, since
fabricating override values here would be false precision. Fallback base per role: condensed
system font (`"Arial Narrow", "Helvetica Neue Condensed", sans-serif`) for Display/Heading, plain
system sans (`Arial, Helvetica, sans-serif`) for Body, system mono stack
(`ui-monospace, SFMono-Regular, Menlo, Consolas, monospace`) for Label/Mono. Verify CLS 0 on a
cold, throttled load of each of the three rendered pairings — not a cached repeat view.

## Research Corrections (vs. `.planning/research/STACK.md`)

Two findings from live verification (Google Fonts `google/fonts` GitHub METADATA.pb +
`fonts.googleapis.com/css2` ranged-request API, both checked 2026-09-25) correct STACK.md's font
research before Phase 1 execution starts:

1. **Barlow Condensed (Pairing B display) and IBM Plex Mono (Pairing B mono) are not variable
   fonts** — Google Fonts ships only static per-weight instances for both (confirmed by an empty
   `axes` block in METADATA.pb, a GitHub file listing showing only `-Thin.ttf` … `-Black.ttf`
   static files, and a `400: Font family not found` response when requesting a `wght` range from
   the live CSS2 API). This does not break DSGN-04's ≤3-file budget — the type system here only
   ever needs one weight per role — but it does mean Pairing B ships two static single-weight
   files where STACK.md assumed two variable files. Ship `BarlowCondensed-Black.ttf` and
   `IBMPlexMono-Regular.ttf` as the source TTFs to subset.
2. **Oswald (Pairing C display) is variable, but its `wght` axis is 200–700, not up to 900** —
   confirmed by METADATA.pb (`min_value: 200.0, max_value: 700.0`) and the live API rejecting a
   `100..900` request for this family. Pairing C's heaviest achievable Display/Heading instance is
   700 (Bold), not a true Black — a real, owner-visible difference from Pairings A and B, noted in
   the Font Pairings table above rather than silently using an out-of-range value that a browser
   would clamp without telling anyone.

Confirmed correct, no change: Big Shoulders Display (100–900), Inter (100–900, +opsz 14–32),
Public Sans (100–900), IBM Plex Sans (100–700, +wdth 75–100), JetBrains Mono (100–800) are all
genuinely variable. Space Mono's static-only status (Pairing C mono) was already correctly flagged
by STACK.md.

## Resolved Spec Conflict — Hero Accent Color

Spec §6.1's band-1 (Hero) row says "Magenta strike through 'the scope'; highlighter hit on 'the
business'" — but the Hero is explicitly a **light** band, and §8/§18 lock "magenta never appears
on white bands" (confirmed above: `#FC0781` on `#F5F6F7` computes 3.54:1, correctly excluded).
This is a direct, unresolved contradiction inside the spec document itself, not a place where one
passage is obviously stale — both statements were written by the same "resolve all conflicts"
pass (§18, dated the same day). Resolution applied here, per this project's own standing rule that
"§18 resolved decisions win": the hero's strike/highlight use the **light-band accent**,
`#07B2B2` teal — which §8 explicitly authorizes for "display type and graphics" on white, exactly
what a strike-through mark and a highlighter-hit shape are. Implementation detail that also
resolves the contrast concern: render both marks as a **decorative layer** (an SVG line / a
highlight shape sitting behind or independent of the glyphs) rather than recoloring the headline
text itself — the underlying text stays the default ink color, so the marks carry no unique
information and sit outside WCAG's text-contrast requirement entirely, which is necessary because
`#07B2B2` on `#F5F6F7` computes 2.42:1 — below even the 3:1 large-text/graphics floor. If a
future phase wants this literally in magenta for some other white-band moment, that would need a
fresh owner decision — it cannot be inferred from this spec as written.
