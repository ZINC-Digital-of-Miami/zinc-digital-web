## Vercel root causes (measured, not guessed)

**Task 1 — original failure (`dpl_Mrt42EZVEgGABUpLFS4gqdh5bFQW`):** Vercel's persisted `node_modules/.astro/fonts` build cache still held resolved-font metadata from the commit before the completeFonts hook and the 9-family Pairing A/B/C config existed. Every Vercel deployment since had failed identically on the same page (404.html — alphabetically first in the hook's `readdir(dir,{recursive:true})` walk, not a 404-specific bug), while every cache-free build (local, CI) always succeeded. The hook itself also had a latent bug: it located the display family's `@font-face` by assuming it was always the first block in a page's inlined CSS rather than matching by font-family name. Fixed by collapsing to Pairing A only (three families) and matching `@font-face` by name.

**Task 3 — recurred failure after Task 1's fix (`dpl_Gvx1KnJfsJhL1LS84Jvaax2PytAf`, then `dpl_BRacC6sZvusQMbVrc1GkL9Z8Xtfc` after an insufficient interim fix):** Same `FONT_OUTPUT_INCOMPLETE: 404.html has 0 active woff2 sources, expected 3. sources=[]` symptom, but local `npm run build` and local `npx vercel build` both passed clean every time — the failure was Vercel-infrastructure-only. Added a one-shot diagnostic dump of the built `<head>` to the `astro:build:done` hook, pushed, and read the actual Vercel build log. It showed:

```
src:url("/_astro/fonts/1a9b0e807a030b79.woff2?dpl=dpl_FsUhKWL8G2PDhpmgfuHGR3ff48UK") format("woff2")
```

Vercel's own build platform appends a `?dpl=<deployment-id>` skew-protection query string to static asset URLs referenced during its build step. The hook's woff2-source regex required the URL to end in `.woff2"` with nothing between the extension and the closing quote, so every match silently failed and `sources.size` came out `0`. Fixed by making the capture group tolerate an optional trailing `?...` before the closing quote; verified the new regex against the exact captured head dump (`sources.size === 3`, `preload === displaySource`) before pushing the real fix. The diagnostic dump was removed in the same commit that fixed the regex.

An interim fix (clearing `node_modules/.astro/fonts` before every build, to guard against exactly the kind of cross-deployment cache staleness Task 1 found) was applied first, verified locally, and pushed — it did not fix this specific failure (the query-string regex bug was untouched by it) but is kept as legitimate defensive hardening against a real, previously-proven caching hazard.
